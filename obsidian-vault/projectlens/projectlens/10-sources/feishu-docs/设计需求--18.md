设计需求
ProjectLens 试点需求说明

一、项目背景

ProjectLens 是面向公司不同部门的项目协作助手，目标不是只帮助开发人员查代码，而是帮助业务、产品、研发、测试和管理者围绕同一个项目事实进行沟通。

项目资料来自飞书文档、飞书多维表格、会议记录和 GitHub。Agent 在群聊中根据用户问题查找资料，并返回有证据支持的项目结论。

二、要解决的问题

需求、开发、测试、发布之间缺乏完整追踪。
产品、研发和测试对项目范围、进度和当前状态理解不一致。
管理者无法快速知道项目风险、阻塞和需要决策的事项。
跨部门沟通依赖人工翻找文档和重复解释。
项目资料分散在多个系统中，历史提议和正式结论容易混淆。
当资料缺失时，团队通常无法判断是没有完成，还是没有记录。

三、试点目标

在 ProjectLens 自身项目上验证以下能力：

用户可以通过自然语言询问项目情况。
Agent 能查找需求文档、多维表格、会议记录和 GitHub 资料。
Agent 能说明当前需求范围、已确认约定和明确排除项。
Agent 能判断是否已经存在开发安排和测试安排。
Agent 能识别风险、阻塞、冲突和资料缺口。
Agent 能提供来源、来源更新时间和证据等级。
对无法证实的问题，Agent 必须明确说明目前没有证据，不能凭空补全。

四、当前范围

只读接入飞书文档。
只读接入飞书多维表格。
读取项目会议记录。
读取 GitHub Issue、Pull Request 和 Commit。
支持用户在群聊中 @ProjectLens 或明确提出项目问题。
Agent 返回当前结论、证据来源、更新时间和不确定性。
Agent 记录无法回答的问题，形成知识缺口，交由项目管理员补充资料。
LLM Wiki 作为源资料的整理和阅读层，不替代正式源文档。

五、资料优先级

需求范围和正式约定：
正式需求文档、飞书多维表格当前记录优先。

开发安排和实现状态：
GitHub Issue、Pull Request、Commit 优先。

测试安排和测试结果：
测试计划、测试记录、验收结果和 CI 记录优先。

会议记录：
用于补充背景、讨论过程和历史提议，不能单独证明事项已经正式确认。

六、明确不在范围内

不自动修改飞书文档、多维表格或 GitHub。
不自动分配开发任务。
不自动改变项目状态。
不替管理者做最终决策。
不为不同角色生成不同事实版本。
角色只用于权限控制，所有有权限的用户应看到同一套事实依据。
试点阶段不引入 GraphRAG，先验证资料质量、来源优先级和证据回答价值。

七、典型使用场景

场景一：业务人员询问“当前需求范围是什么？”

Agent 应返回：
当前正式需求范围
已确认的业务约定
明确不包含的内容
对应需求文档和多维表格记录
是否存在范围冲突

场景二：产品人员询问“这个需求是否已经安排开发和测试？”

Agent 应分别查找：
GitHub Issue 或 PR
项目计划
测试安排
测试负责人和执行结果

如果只有会议中提过，但没有正式记录，应标记为“会议提议，尚未确认”。

场景三：研发人员询问“当前项目有什么阻塞？”

Agent 应综合：
项目计划
会议纪要
GitHub 状态
测试资料缺口
逾期事项

并区分事实、推断和待确认事项。

场景四：管理者询问“本周需要决策什么？”

Agent 应列出：
当前风险
当前阻塞
逾期事项
影响范围
需要谁决策
决策依据
缺失的证据

八、回答要求

每个回答尽量包含以下结构：

当前结论
主要依据
来源和更新时间
已确认事项
未确认事项
冲突或不一致
当前缺失的资料
建议下一步

九、验收标准

对需求范围问题至少返回一条可定位证据。
对开发安排问题必须区分 Issue、PR、Commit 和会议提议。
对测试安排问题必须区分测试计划、测试执行结果和 CI 证据。
能区分正式确认、历史提议、当前推断和未知。
发现来源冲突时，同时展示冲突来源，不强行合并。
对没有证据的问题明确回答“目前没有证据”。
未授权用户不能读取权限范围外的资料。
每个知识缺口应记录问题、影响、需要补充的资料和责任人。
