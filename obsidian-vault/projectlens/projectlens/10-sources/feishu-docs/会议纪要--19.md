会议纪要
ProjectLens 试点启动会纪要

会议日期：2026-09-10

会议主题：确认 ProjectLens 的业务方向、试点范围、资料来源和验证方式。

参会角色：产品、业务代表、研发代表、测试代表、项目管理员。

一、会议目标

明确 ProjectLens 不是单纯的开发问答工具。
明确不同部门如何使用项目助手。
确认项目资料的来源和优先级。
确认 Agent 如何处理冲突和资料缺失。
确认试点阶段不做过度技术建设。

二、已确认决策

ProjectLens 面向业务、产品、研发、测试和管理者等不同角色。
首个试点项目使用 ProjectLens 自身。
项目资料包括飞书文档、飞书多维表格、会议记录和 GitHub。
Agent 使用正常证据回答，不按角色生成不同事实。
角色只用于权限控制，不改变事实本身。
回答必须显示证据来源和更新时间。
资料不足时，Agent 必须明确说明不确定性。
无法回答的问题需要记录为知识缺口。
正式需求文档和多维表格优先作为需求事实来源。
GitHub 优先作为开发事实来源。
测试记录、验收结果和 CI 记录优先作为测试事实来源。
会议纪要用于记录背景、讨论和提议，不能单独作为完成证明。
LLM Wiki 只作为资料整理层，源文档仍然是事实依据。
试点阶段暂不引入 GraphRAG。

三、跨部门使用方式

业务部门：
查询需求范围、当前状态、已确认约定和待确认事项。

产品部门：
查询需求是否已进入开发、开发范围是否发生变化、哪些事项需要再次确认。

研发部门：
查询 Issue、PR、Commit、开发安排、阻塞和依赖关系。

测试部门：
查询测试安排、测试资料、验收结果和当前测试缺口。

管理者：
查询项目风险、阻塞、逾期事项、决策事项和证据缺口。

四、尚未确认的事项

是否在试点第二周接入其他项目。
是否自动生成项目周报。
是否支持 Agent 通过审批后修改任务状态。
是否接入更多外部系统。
是否在后续阶段引入 GraphRAG。

以上事项均不是当前正式范围，不能当作已经确认的项目计划。

五、当前风险

GitHub 仓库和 Issue、PR、Commit 的完整链接尚未全部整理。
测试负责人和测试执行结果尚未形成正式记录。
CI 运行结果尚未接入资料库。
部分历史会议内容可能与正式需求存在差异。
文档权限边界还需要进一步确认。

六、行动项

项目管理员：
维护试点资料，标注来源类型、优先级、状态和更新时间。

研发代表：
补充 GitHub 仓库、Issue、PR 和 Commit 的引用信息。

测试代表：
建立测试安排和测试缺口记录。

产品代表：
检查正式需求文档与会议记录是否存在范围冲突。

管理者：
确认后续是否需要接入更多项目。

七、文档属性

文档类型：会议纪要

证据等级：中
