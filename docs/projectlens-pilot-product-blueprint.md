# ProjectLens 真实项目试点版产品蓝图

更新时间：2026-09-08

## 1. 产品定位

ProjectLens 不是“项目问答机器人”，也不是要求团队重新维护一套 Wiki 的知识管理工具。

它是一个以项目为上下文、以协作群为工作现场、以已有资料为依据的跨部门项目助手：

```text
业务、产品、研发、测试在同一个项目群里讨论
-> @ProjectLens
-> Agent 读取当前项目的已授权资料
-> 给出当前最可信的共同上下文
-> 标出冲突、缺失和无法确认项
-> 用来源支持结论，并记录知识缺口
```

第一阶段不让 Agent 自动改变需求、进度、测试或发布状态。它先证明自己能让不同角色基于同一组资料更快理解和讨论项目。

## 2. 试点边界

### 2.1 试点对象

- 一个真实软件项目；
- 一个包含业务、产品、研发、测试的飞书协作群；
- Agent 只在被 `@` 或明确提问时响应；
- 首批资料来自飞书文档、飞书多维表格、会议纪要和 GitHub。

### 2.2 第一阶段问题

Agent 重点回答三类问题：

1. 当前需求范围和已有约定是什么？
2. 这项需求目前有没有开发和测试安排？
3. 不同资料不一致时，当前更可信的结论是什么，依据是什么？

### 2.3 明确不做

- 不自动修改原始飞书文档、多维表格或 GitHub；
- 不自动分派任务或代表团队做决策；
- 不把普通群聊内容直接升级为正式项目事实；
- **明确不建设 GraphRAG**：项目不把 GraphRAG 作为产品能力或后续默认路线；需要的关联先用结构化元数据、来源链接和 Wiki 页面引用解决。
- 不把 LLM Wiki 当作唯一事实来源。

## 3. 核心用户价值

### 业务和产品

- 不需要先理解代码，就能知道需求目前的范围、约定和实现安排；
- 发现需求描述与开发/测试安排之间的空白；
- 讨论时能快速引用历史会议和已有资料。

### 研发

- 快速了解需求背景、验收边界和已有技术约定；
- 判断一个需求是否已经有 Issue、PR 或开发安排；
- 减少反复向产品确认“到底要做什么”的时间。

### 测试

- 判断需求是否已经形成可验证的验收条件；
- 发现需求有定义但没有测试安排的情况；
- 追溯测试依据来自哪一版需求或会议结论。

### 项目负责人和管理者

- 看到资料之间的冲突和协作缺口，而不是只看到一份貌似完整的总结；
- 快速识别哪些问题已有结论、哪些问题仍待补充证据；
- 了解项目当前共识的可靠程度。

## 4. 产品行为契约

每次群聊回答都应尽量遵循以下结构：

```text
结论：当前最可信的项目事实

依据：采用了哪些资料、版本和更新时间

当前范围/约定：从资料中确认到的内容

开发与测试安排：已记录的安排，或明确说明没有找到

冲突与不确定性：哪些资料不一致、哪些问题不能确认

知识缺口：需要补充什么证据，缺口影响什么
```

回答必须区分：

- `confirmed`：由权威来源支持的当前事实；
- `observed`：从资料中观察到，但还没有被确认为当前事实；
- `proposed`：会议或 Agent 提出的候选变化；
- `conflicted`：来源之间存在冲突；
- `stale`：资料可能已经过期；
- `unknown`：当前授权资料不足以回答。

Agent 不应为了显得完整而填补未知项。高质量回答可以明确说“当前无法确认”，但必须说明缺什么。

## 5. 知识库形态

知识库采用三层结构，但产品上不把它们包装成三个孤立系统：

```text
原始资料层
  飞书文档 / 多维表格 / 会议纪要 / GitHub

项目共同认知层
  LLM Wiki：按资料类型整理、摘要、关联、标注冲突

Agent 使用层
  ProjectLens Evidence + RAG 检索 + Hermes 群聊回答
```

### 5.1 原始资料层

原始资料必须保留：内容、来源、版本、更新时间、权限和内容哈希。LLM 不覆盖原始资料。

### 5.2 LLM Wiki 层

Wiki 按资料类型组织：

```text
项目 Wiki
├── 需求资料
├── 多维表资料
├── 会议纪要
├── 开发资料
├── 测试资料
├── 发布资料
└── 项目规则与术语
```

每个页面至少包含：

- 当前整理；
- 原始来源与版本；
- 最近更新时间；
- 关联资料；
- 冲突与待确认项；
- 页面内容状态。

Wiki 是可读的项目共同认知，不是新的正式事实源。它的每条结论都必须能回到原始来源。

### 5.3 Agent 使用层

Hermes 不直接读数据库、向量索引或任意文件系统，而是通过 ProjectLens 受权限约束的只读工具获取 Evidence 和 Wiki 摘要。

## 6. 资料优先级

优先级按“事实类型”定义，而不是给所有资料一个统一排名：

| 事实类型 | 首选来源 | 次级来源 | 仅作线索 |
| --- | --- | --- | --- |
| 需求范围/验收条件 | 正式需求文档、需求多维表 | 已归档会议纪要 | 普通群聊 |
| 需求状态/排期 | 项目计划表、需求表状态 | 会议纪要 | Agent 推断 |
| 开发进度 | GitHub Issue、PR、Merge 记录 | 开发讨论 | 需求文档中的计划 |
| 测试状态 | 测试记录、验收结果 | 测试讨论 | GitHub 已合并 |
| 技术决策 | 已确认 ADR、正式技术方案 | 会议纪要 | 临时讨论 |
| 负责人 | 项目成员表、任务分派记录 | 会议纪要 | 代码作者推断 |

优先级只是默认判断规则，还要结合版本、更新时间、适用范围和 `status`。如果冲突不能消解，Agent 必须同时展示更可信结论和冲突来源。

## 7. 最小资料元数据

所有进入知识库的资料统一补充：

```text
source_id
source_type
project_id
title
topic
owner
status
authority_scope
revision
observed_at
effective_from
effective_to
supersedes
related_sources
access_scope
```

其中 `authority_scope` 表示“这份资料对哪类事实具有权威性”，而不是简单地表示整份资料都可信。

## 8. 更新与审核策略

采用：**原始资料自动同步，LLM Wiki 自动生成草稿，低风险内容自动发布，高影响事实审核后生效。**

### 可自动发布

- 资料目录和摘要；
- 会议主题、关键词和时间线；
- 资料之间的关联；
- 冲突提示和知识缺口；
- 原始资料的检索入口。

### 必须审核后生效

- 需求范围和验收标准；
- 开发进度和任务归属；
- 测试是否通过；
- 发布状态；
- 正式技术决策；
- 风险等级和截止时间。

“审核”不是让管理员重写所有页面，而是确认某条候选结论是否可以成为当前项目共识。

## 9. 知识缺口闭环

不能只记录“搜索不到”，要记录可处理的缺口：

```text
knowledge_gap
- question
- project
- fact_type
- missing_or_conflicting_sources
- impact
- suggested_source_type
- detected_at
- status
```

示例：

```text
问题：客户分层规则 B 是否已经生效？
缺口类型：需求范围确认
原因：会议纪要与需求表不一致
建议补充：更新需求多维表，或标记会议结论为未生效
影响：可能影响开发拆分、测试用例和发布日期
```

知识缺口是管理员和团队改进知识库的入口，也是衡量 Agent 是否真正发现协作问题的重要产物。

## 10. 第一阶段验收指标

不要只测“回答是否流畅”，要测是否减少了真实沟通成本：

- 需求范围问题的有效回答率；
- 有来源依据的事实比例；
- 资料冲突被正确标记的比例；
- 开发/测试安排查询的准确率；
- 未知项和知识缺口的漏报率；
- 跨项目、跨群、越权资料泄露数，必须为 0；
- 团队成员为确认项目背景而产生的重复追问次数；
- 从提问到获得可继续讨论的共同上下文所需时间。

试点前准备一组真实历史问题，分别标注：正确结论、应使用的来源、不可泄露内容和必须声明的未知项。每次更换提示词、检索策略或模型都回放这组问题。

## 11. 分阶段落地

### Phase 1：资料接入与共同认知

- 接入一个项目的飞书文档、多维表格、会议纪要和 GitHub；
- 建立统一元数据和来源优先级；
- 生成按资料类型组织的 LLM Wiki 草稿；
- Hermes 在群中回答三类核心问题；
- 记录冲突和知识缺口。

### Phase 2：协作理解增强

- 让 Wiki 页面关联需求、开发、测试资料；
- 增加角色化表达：业务看范围和影响，研发看实现依据，测试看验收依据；
- 支持从一次群聊问题回溯到原始资料和版本。

### Phase 3：协作推进

- 在人确认后生成任务、风险和决策草案；
- 形成项目状态摘要和待决策清单；
- 对发布前的资料完整性做只读检查。

### 明确不做：GraphRAG

本产品不建设 GraphRAG。需求、开发、测试、会议和发布资料之间的关联，统一通过协作对象标识、结构化元数据、来源链接、版本和状态表达。这样可以降低维护成本，避免为了技术完整性引入团队无法理解和维护的图谱系统。

## 12. 对现有 ProjectLens 的映射

- `ProjectSpace`：定义试点项目、来源、权限和群绑定；
- `Evidence` / `EvidenceIndex`：保存原始来源和可引用证据；
- `ContextEngine`：做权限过滤和混合检索；
- `ProjectMemory`：只保存经审批的稳定项目事实；
- `KnowledgeGapReport`：承载资料缺失和冲突发现；
- Hermes ProjectLens tools：向群聊 Agent 提供受限只读上下文；
- `Verifier`：确保回答中的事实可回溯到真实来源；
- Feishu adapter：只负责群消息入口和结果呈现，不直接读知识库。

## 13. 产品判断

ProjectLens 的第一价值不是“让模型知道更多”，而是：

> **让不同部门在讨论同一个项目问题时，能看到同一组有来源、带状态、可追溯的共同上下文。**

因此，第一版应优先投资资料治理、Wiki 草稿、冲突识别、知识缺口和引用质量；不要先投资复杂图数据库或更多问答模板。
