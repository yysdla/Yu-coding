# ProjectLens 产品文档

**版本**：V1.0  
**更新时间**：2026-09-09  
**文档性质**：产品与研发共用总纲

## 1. 产品定义

ProjectLens 是一个以项目为上下文、以群聊为工作现场、帮助公司不同角色建立共同认知并推进协作的 Project Copilot。

它把项目相关的文档、会议纪要、多维表格、代码、任务、发布记录和项目记忆组织到同一个 ProjectSpace 中，在权限范围内回答问题、核对事实、发现冲突、暴露知识缺口，并推动讨论形成明确的决策和行动。

ProjectLens 不是单纯的代码问答工具、Wiki 系统、RAG 搜索系统或自动项目管理系统。它是这些能力之上的项目协作层。

核心闭环是：

```text
资料进入
-> 持续整理和关联
-> 形成带来源的项目上下文
-> 在群聊中核对事实
-> 暴露冲突和知识缺口
-> 形成决策和行动
-> 将确认结果重新沉淀回项目
```

## 2. 要解决的问题

企业项目中的信息通常分散在不同系统中：

- 需求在文档或多维表格中；
- 方案和变更在会议纪要与群聊中；
- 实现在代码仓库和 PR 中；
- 进度在任务系统中；
- 发布和事故在运维系统中；
- 关键约定只存在于少数人的记忆里。

由此产生四类成本：

1. **信息查找成本**：需要反复找人、翻文档、搜索代码和确认最新状态。
2. **角色理解成本**：业务、产品、研发、测试和管理者对同一项目使用不同语言，难以形成共同判断。
3. **上下文丢失成本**：会议结论、临时约定和历史决策没有可靠地沉淀，后续讨论重复发生。
4. **风险暴露成本**：需求、代码、任务和发布状态出现不一致时，往往到延期、事故或返工后才被发现。

ProjectLens 的目标不是替团队做所有决定，而是让团队更快获得可靠上下文，减少无效确认，并尽早暴露不确定性。

## 3. 产品目标与非目标

### 3.1 产品目标

- 让团队围绕同一个项目共享可追溯的上下文。
- 让用户在飞书群聊中直接提出项目问题，不依赖复杂命令。
- 让不同角色看到适合自己的表达，但共享同一组事实、证据和未解决问题。
- 让 Agent 明确区分事实、推断、冲突、未知和建议。
- 让会议和讨论能够转化为确认事项、决策、任务和项目记忆。
- 让项目状态、知识缺口和风险持续更新，而不是只在需要时临时搜索。

### 3.2 非目标

当前阶段不做以下事情：

- 不做全公司的通用聊天机器人。
- 不把所有资料无差别丢入向量库。
- 不把 LLM 生成的 Wiki 当成正式事实源。
- 不自动修改代码、创建 PR、部署、回滚或重启生产系统。
- 不自动给员工分配任务或替管理者做关键决策。
- 不为了技术完整性提前建设复杂 GraphRAG。
- 不全量监听并总结所有群聊消息。

## 4. 目标用户与使用价值

### 4.1 业务与产品人员

关注需求范围、业务规则、用户影响、当前进度、延期原因和需要配合的事项。

典型问题：

- 这个需求现在做到哪一步了？
- 目前实现和需求文档是否一致？
- 这次变更会影响哪些用户和业务流程？
- 还有哪些问题需要产品确认？

### 4.2 研发人员

关注模块关系、调用链、代码变更、实现约束、错误原因、测试范围和负责人。

典型问题：

- 这个接口为什么会报错？
- 最近哪些提交影响了订单流程？
- 这个需求涉及哪些模块和测试？
- 当前阻塞点是谁负责，依赖什么信息？

### 4.3 测试与质量人员

关注验收标准、实现范围、回归范围、失败用例、环境和发布风险。

典型问题：

- 这个需求应该覆盖哪些测试场景？
- 当前实现是否满足已确认的验收标准？
- 哪些风险还没有测试证据？

### 4.4 项目负责人和管理者

关注里程碑、风险、阻塞、负责人、决策点和跨团队依赖。

典型问题：

- 项目当前状态是什么？
- 最大的延期风险在哪里？
- 哪些事项需要我决策或协调？
- 最近的会议结论是否已经落实？

### 4.5 新成员与跨部门协作者

关注项目背景、术语、模块地图、职责边界和推荐阅读路径。

典型问题：

- 这个项目是做什么的？
- 哪些模块最重要？
- 我应该先看哪些资料？
- 某个业务术语在系统里对应什么？

## 5. 核心产品概念

### 5.1 ProjectSpace

ProjectSpace 是项目的统一上下文边界。每个项目独立配置自己的资料来源、成员、权限、术语、记忆和连接器。

一个 ProjectSpace 至少包含：

- 项目标识和显示名称；
- Git 仓库、分支和版本范围；
- 飞书文档和会议纪要；
- 多维表格、任务和发布记录；
- 事故、日志或其他运营信号；
- 检索和图谱命名空间；
- 项目记忆命名空间；
- 文件读取白名单；
- 成员角色与来源可见性策略；
- 飞书群聊绑定。

更换项目时应更换 ProjectSpace 配置，而不是修改 Agent 逻辑。

### 5.2 LLM Wiki

LLM Wiki 是项目资料的整理和解释层，不是第二个事实源。

它负责：

- 将不同来源整理成项目概览、模块说明、术语表和时间线；
- 建立需求、决策、任务、代码、发布和负责人之间的关联；
- 识别重复、冲突、过期和缺失内容；
- 为用户提供易读的项目导航和阅读路径；
- 保留每一项整理结果的原始来源和更新时间。

LLM Wiki 中的内容必须有明确状态：

| 状态 | 含义 |
|---|---|
| `proposed` | Agent 根据资料整理出的候选内容，尚未确认 |
| `confirmed` | 已由有权限的人员确认 |
| `conflicted` | 不同来源存在冲突 |
| `superseded` | 已被更新版本替代 |
| `expired` | 已过期，不应作为当前结论 |

高影响事实不能由模型直接覆盖。模型只能提出更新建议，正式变更需要人工确认或来源系统同步。

### 5.3 Evidence

Evidence 是回答中每个重要判断的依据。它至少记录：

- 来源系统和来源地址；
- 原始内容或结构化字段；
- 版本、更新时间和观察时间；
- 项目与权限范围；
- 来源类型和事实类型；
- 可靠性和引用关系。

没有 Evidence 的内容不能作为已确认事实输出，只能降级为推断、未知或待确认事项。

### 5.4 项目知识对象

项目中的重要内容应逐步抽象成可关联的知识对象：

```text
Requirement   需求
Decision      决策
Task          任务
Risk          风险
Question      待确认问题
Fact          项目事实
Owner         负责人
Release       发布
Incident      事故
Term          业务术语
```

这些对象可以通过引用和简单关系连接起来，例如：

```text
需求 -> 对应模块 -> 产生任务 -> 由负责人处理 -> 包含在发布中
事故 -> 影响模块 -> 关联提交 -> 产生复盘决策
决策 -> 修改业务规则 -> 需要同步需求文档和验收标准
```

这套结构优先服务于可解释的项目协作，不要求第一阶段建设完整图数据库。

## 6. 来源与可信度模型

不同事实类型的权威来源不同，不能使用一张全局来源排序表。

| 事实类型 | 通常优先的来源 |
|---|---|
| 正式需求 | 已确认需求文档、需求表 |
| 当前实现 | 代码、发布版本、测试结果 |
| 负责人 | 项目成员表、任务系统 |
| 当前进度 | 任务表、发布记录、会议确认 |
| 会议结论 | 已确认会议纪要 |
| 临时讨论 | 群聊消息，默认只能作为候选依据 |
| 运行状态 | 监控、日志、发布和事故系统 |

Agent 需要同时保留：

- `source_created_at`：来源创建时间；
- `source_updated_at`：来源更新时间；
- `observed_at`：系统观察到该状态的时间；
- `valid_from` / `valid_to`：结论有效时间范围。

回答中应明确区分：

- 已确认事实；
- 基于多条证据的推断；
- 不同来源的冲突；
- 当前缺失的信息；
- 建议的下一步。

示例：

```text
结论：会议中提出了新的业务规则。
当前状态：待确认，暂不能视为正式生效规则。
依据：最新会议纪要。
冲突：正式需求文档和多维表格尚未更新。
下一步：请产品负责人确认是否纳入本期需求，并同步正式资料。
```

## 7. 系统职责边界

### 7.1 Hermes Runtime

Hermes 是通用 Agent 运行时，负责：

- 飞书消息接入和会话；
- 用户意图理解；
- 模型调用和工具循环；
- 多轮上下文和压缩；
- Agent profile 和插件路由；
- 回复生成和交互呈现。

Hermes 不直接决定项目事实、项目权限或来源可信度。

### 7.2 ProjectLens Kernel

ProjectLens 是项目智能内核，负责：

- ProjectSpace 和项目绑定；
- 角色、群聊可见性和有效权限范围；
- 文档、代码、表格、任务等资料接入与检索；
- Evidence、来源优先级和证据链；
- 冲突、知识缺口和项目风险；
- 项目记忆及其审批；
- 回答引用校验、事实校验和审计。

ProjectLens 不重复实现完整的通用 Agent Runtime。

### 7.3 RAG

RAG 负责从文档、会议纪要、代码和其他文本资料中找到相关证据。它是检索能力，不是产品边界。

对于多维表格、任务状态和发布记录，应优先使用结构化查询，再结合文本证据解释结果。


## 8. 权限与角色原则

权限必须在检索前进入 Agent 上下文，而不是生成回答后再过滤。

本次有效权限由三部分共同决定：

```text
用户角色权限 ∩ 群聊可见范围 ∩ 项目资源权限
```

需要区分：

- `ProjectMemberRolePolicy`：用户在项目中的角色、可读来源和回答风格；
- `ChatVisibilityPolicy`：当前群聊允许公开的内容范围；
- `EffectiveAccessScope`：本次请求实际生效的权限。

示例：

- 开发私聊：可以查看详细代码、错误栈和内部调用关系；
- 业务与开发混合群：可以看到业务影响和处理状态，但不应公开敏感日志；
- 产品角色：优先得到范围、进度、影响和待确认事项；
- 管理角色：优先得到风险、阻塞、负责人和决策点。

角色不是最后的卡片过滤器。角色策略必须影响 Agent 调查什么、如何表达以及哪些内容可以展示。

## 9. 核心用户流程

### 9.1 项目状态核对

```text
用户询问项目状态
-> 解析 ProjectSpace 和角色
-> 查询任务、发布、会议、代码变化和风险
-> 合并证据
-> 输出进展、阻塞、负责人、风险和依据
```

### 9.2 需求讨论与事实核对

```text
用户提出需求问题
-> 查正式需求、会议讨论、任务和现有实现
-> 区分已确认内容、临时讨论和冲突
-> 输出缺失信息和需要确认的人
-> 在用户确认后更新项目知识对象
```

### 9.3 会议到行动

```text
会议结束
-> 识别事实、决定、分歧和待办
-> 生成决策与任务草案
-> 指定建议负责人和截止时间
-> 相关人员确认
-> 写入项目状态或外部任务系统
```

### 9.4 工程问题调查

```text
用户提供错误、PR 或发布信息
-> 查询相关模块、提交、测试和运行信号
-> 形成候选原因
-> 校验证据和项目权限
-> 输出可能原因、影响、未知和验证路径
```

## 10. 标准回答结构

内部回答必须先形成结构化结果，再生成适合群聊的自然语言。

```text
Answer
- conclusion       一句话结论
- facts            已确认事实，每条带引用
- inferences       推断，明确标注推断依据
- conflicts         来源冲突
- unknowns          当前未知和缺失资料
- impact            对业务、技术或进度的影响
- next_actions      建议下一步和需要谁确认
- citations         来源和版本
- visibility_scope  可展示范围
- policy_used       使用的角色和权限策略
```

默认群聊回复优先展示：

1. 结论；
2. 影响；
3. 冲突或未知；
4. 下一步；
5. 可展开的依据。

详细证据、审计和工具轨迹不应挤占首屏，但必须可追溯。

## 11. MVP 范围

第一阶段建议聚焦一个真实项目，接入三类来源和三类角色：

### 11.1 来源

- 飞书文档和会议纪要；
- 一个飞书多维表格；
- 一个 GitHub 仓库。

### 11.2 角色

- 研发；
- 产品/业务；
- 项目负责人或管理者。

### 11.3 必须支持的场景

- 项目介绍和新人理解；
- 项目当前状态查询；
- 需求范围和实现状态核对；
- PR、提交或发布影响分析；
- 负责人和阻塞查询；
- 会议结论、冲突和待办提取；
- 带来源回答；
- 知识缺口记录；
- 角色和群聊权限控制。

### 11.4 MVP 明确不支持

- 自动修改代码；
- 自动创建或合并 PR；
- 自动部署和回滚；
- 无审批写入正式需求或项目记忆；
- 无边界的全量群聊监听；
- 跨全公司的开放式知识搜索。

## 12. 产品路线图

### Phase 0：方向和合同冻结

目标：统一产品边界和核心对象。

产出：

- ProjectSpace、Evidence、Answer、Run、Approval 等合同；
- 明确来源优先级和事实状态；
- 明确 Hermes 与 ProjectLens 的职责边界；
- 建立一个真实项目的评估数据集。

### Phase 1：资料接入与 LLM Wiki

目标：让项目资料可以持续进入、整理、关联和追踪。

产出：

- 文档、GitHub、多维表格连接器；
- 原始资料保存和版本追踪；
- Wiki 候选内容、引用和状态；
- 冲突、过期和知识缺口检测。

### Phase 2：群聊只读问答

目标：让用户在飞书自然语言提问，并获得带依据的答案。

产出：

- 群聊到 ProjectSpace 的绑定；
- 用户角色和群聊可见性解析；
- Hermes 调用 ProjectLens 只读工具；
- 事实、推断、未知、冲突和下一步的回答结构。

### Phase 3：协作闭环

目标：把讨论转成确认事项、决策和行动。

产出：

- 会议和群聊中的决策、分歧、待办识别；
- 任务草案和负责人建议；
- 人工确认后写入任务或项目记忆；
- 项目状态和知识缺口持续更新。

### Phase 4：风险与项目快照

目标：让 Agent 主动发现有证据的项目风险。

产出：

- 需求、任务、代码和发布状态不一致检测；
- 阻塞依赖、延期、无人负责和文档过期检测；
- 项目快照、时间线和风险摘要；
- 只在状态变化或需要行动时通知。

### Phase 5：受控工程执行

目标：在只读能力稳定后，提供可审批的工程建议。

产出：

- patch plan；
- test plan；
- PR 草案；
- 隔离工作区验证；
- 明确的审批、回滚和审计链路。

真正的 Apply、PR、部署、回滚和生产操作必须经过人工审批。

## 13. 产品质量指标

### 13.1 可信度指标

- 事实引用覆盖率；
- 引用来源准确率；
- 未知和冲突识别准确率；
- 越权检索和越权展示次数；
- 用户纠正回答的比例；
- 过期事实被继续使用的比例。

### 13.2 协作效率指标

- 从问题提出到形成可执行结论的平均时间；
- 重复询问和重复开会的减少比例；
- 会议后形成明确任务的比例；
- 知识缺口被补齐的比例；
- Agent 建议被人工采纳的比例；
- 用户从答案跳转到原始依据的比例。

### 13.3 使用指标

- 周活跃项目数；
- 每个项目的有效问答数；
- 多角色共同参与的讨论数；
- 项目资料同步成功率；
- 高价值问题的解决闭环率。

最重要的业务指标是：

> 一次跨部门项目问题从提出到形成可靠、可执行结论，平均节省了多少时间。

## 14. 风险与控制

### 信息错误

控制方式：强制引用、事实状态、来源优先级、未知显式化和回答验证。

### 权限泄露

控制方式：检索前 ACL、用户与群聊权限交集、不同受众的展示范围、默认只读。

### 知识污染

控制方式：原始资料不可覆盖、Wiki 候选状态、人工确认、记忆审批和版本追踪。

### 过度自动化

控制方式：先解释，再提出建议；写操作经过验证和审批；生产操作始终保留人工控制。

### 群聊噪声

控制方式：只在被提问、讨论形成结论或出现高价值状态变化时响应，不全量打断对话。

### 组织不采纳

控制方式：先解决高频、可验证的问题；回答短而清晰；提供原始依据；让用户可以纠正并反馈。

## 15. 成功标准

ProjectLens 第一阶段成功，不是因为它能回答所有问题，而是因为在一个真实项目中，它能够稳定完成以下闭环：

```text
资料接入
-> Wiki 整理
-> 来源优先级判断
-> 群聊提问
-> 输出结论、依据和不确定性
-> 记录冲突与知识缺口
-> 补充资料后自动更新上下文
```

用户应该能够感受到：

- 不需要反复问“谁知道这个”；
- 不需要重新翻几份互相矛盾的资料；
- 能清楚知道哪些已经确定，哪些还没有确定；
- 能明确知道下一步需要谁补充什么；
- 讨论结果能够回到项目上下文中，而不是随着聊天结束消失。

## 16. 一句话产品定位

> **ProjectLens 是一个以 ProjectSpace 为核心、以群聊为工作现场、以原始资料和证据为基础，帮助不同角色建立共同认知、核对项目事实并推进协作的 Project Copilot。**
